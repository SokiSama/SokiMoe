最近想做一个游戏时长统计工具，起因很简单：PlayStation 和 Nintendo Switch 都有自己的游玩记录，但数据分散在两个平台里。看某一款游戏的累计时长还算方便，想回头看看一个月主要玩了什么、两个平台各花了多少时间，就得来回翻。时间久了，也很难看出这些数字是怎么一点点涨上去的。

我想做的，就是把这些记录放到一起，慢慢存下来。第一版只考虑 PlayStation 和 Switch，不做奖杯、成就、攻略，也先不接 Steam 和 Xbox。项目会开源，前端打算放在 GitHub Pages，暂时不绑域名。能把同步和记录做好，就已经达到最初的目的了。

## 先看看数据能不能拿到

这个项目最先要解决的不是页面，而是数据来源。

PlayStation 这边准备尝试社区维护的 [psn-api](https://github.com/achievements-app/psn-api)，通过它读取游戏列表、累计游玩时长和平台信息。不过，这套接入方式依赖社区维护，不能默认接口会一直稳定。正式往下做之前，还是得先把认证、分页、时长字段这些东西逐个跑通。

Switch 这边，我目前更倾向于使用 Nintendo Switch Parental Controls，也就是家长控制产生的使用记录。计划通过 [nxapi](https://github.com/samuelthomas2774/nxapi) 的 `nxapi/moon` 模块接入，先验证设备列表和每日、每月摘要里有哪些可用数据。这也意味着，Switch 主机需要提前绑定家长控制。至于能读取多少历史、记录具体到什么程度，都要等实际测试后再确定，不能先把页面画出来，再假设接口刚好能提供想要的东西。

## 同样是时长，记法却不一样

两边的数据不能直接按同一种方式处理。

PSN 这边准备保存累计时长快照。每次同步，都记下当前累计值和同步时间，再用前后两次的差值计算新增时长。

这里有个容易忽略的问题：累计值增加了，只能说明两个同步点之间多了一段时间，不能据此断定这些时间全部发生在某一天。平台更新可能有延迟，离线游玩的记录也可能稍后才出现。图表可以展示变化，但不该把它包装成精确的每日游玩日志。

第一次同步时已经存在的累计时长，也只会作为起点保存。PlayTrace 能持续记录的是之后的变化，过去的时间不会被硬塞进某个月份里。

Switch 如果能拿到家长控制的每日使用记录，就按日期保存，再汇总成月度和年度统计。不过，设备记录和个人账号记录也需要区分；如果数据源无法准确判断是谁玩的，页面就应该如实说明。以前没有记录下来的历史，也不会因为绑定了 PlayTrace 就突然补齐。这一点需要在设计时讲清楚。

## 页面简单一点，记录认真一点

技术栈准备以 TypeScript 为主。前端用 React 和 Vite，后端用 Node.js 和 Fastify，数据库用 PostgreSQL，配合 Drizzle ORM。如果后面需要 Android 版本，再通过 Capacitor 包装现有前端。

后端会分成 API 和同步 Worker。API 负责查询、设置和接收手动同步请求，Worker 负责访问两个平台、刷新认证信息和写入数据库。同步任务计划用 BullMQ 和 Redis 管理，避免自动同步和手动刷新同时访问同一个账号或设备。

前端可以放在 GitHub Pages，后端、数据库和同步任务则需要另外部署，准备先用 Docker Compose 管起来。

两个平台也会各有一层 Adapter，把原始返回值转换成项目内部的数据结构。以后接口字段变了，尽量在对应的接入层处理，减少对统计逻辑和页面的影响。不过，我不打算为了统一而把所有数据都塞进一张表。游戏名称、平台、封面这些基础信息可以共用结构；PSN 的累计快照和 Switch 的每日记录，还是各自保存更合适。

## 跨平台的同一款游戏，先分开存

同一款游戏可能出现在两个平台上，但不能只看名字相同就自动合并。不同版本、重制版和地区名称，都可能造成误判。底层会先保留每个平台自己的游戏 ID 和记录，再考虑增加关联关系。确认属于同一款游戏之后，页面可以展示合计时长，也能展开查看各个平台的数据。

这个功能可以晚一点做。第一版先把每个平台的记录存对，比急着合并更重要。页面也不准备铺得太大：一个总览，一个游戏库，再加游戏详情和统计页。

总览看累计时长、最近游玩的游戏和近期变化；游戏库支持按平台筛选，按时长或最近游玩时间排序；详情页展示单款游戏的记录。月度、年度统计也会做，但能展示到什么粒度，要服从数据本身的能力。尤其是 PSN，不能为了凑出一张每日趋势图，就假装有精确到每天的记录。

## 同步失败，也要看得出来

长期记录最怕的不是偶尔同步失败，而是失败了却没人知道。

如果接口没返回时长，就应该记为未知，而不是零。某一天没有成功获取 Switch 数据，也不能直接当成那天没玩。页面会显示最近一次成功同步的时间，以及当前是否需要重新认证，避免留下一组看起来正常、实际已经很久没更新的数字。同步频率先保守一些，等跑起来再调整。Switch 的每日记录还会定期回查最近几天，处理后续更新。重复同步同一条记录时直接更新，避免每刷新一次，数据库就多出一份数据。

认证信息只留在后端，前端和 Android 使用 PlayTrace 自己的登录会话。需要长期保存的凭据会加密，日志里也不记录这些内容。

## 先让它跑起来

开发顺序已经比较明确了：先写两个小程序，分别验证 PSN 和 Nintendo 的数据，再做数据库和同步任务。等后台连续跑过一段时间，确认记录能更新、重复同步不会产生重复数据、失败后能够恢复，再开始认真做页面。Android 则放到最后，等 Web 版本用顺手了再打包。

目前还是一个准备动手的项目，这篇文章更像是给自己留下的开发笔记。很多细节还得靠实际数据来决定，现在没必要把所有东西都定死。我希望它最后成为一个平时不用怎么照顾的小工具：后台定期同步，想看时就打开。过一阵子回头翻，能知道哪些游戏玩得最多，某段时间的游玩习惯又有什么变化。先把记录留下来，其他功能以后再说。
